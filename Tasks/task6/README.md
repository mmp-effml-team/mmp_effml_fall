Context parallelism (CP) делит между рангами не батч, а каждую последовательность: у каждого из N рангов своя
часть токенов. Всё, кроме attention, обрабатывает токены независимо и разбиения не замечает. Attention же нужны
ключи и значения всей последовательности, и их надо как-то собрать. В этом задании вы добавите CP в учебный
фреймворк `mtf` (в нём уже есть DDP и FSDP) и реализуете три способа это сделать:

1. **all-gather** K и V: самый простой, сначала проверяем на нём данные (часть 1);
2. **ring attention**: блоки K/V ходят по кольцу через P2P-операции, результаты сливаются online softmax (часть 2);
3. **Ulysses**: all-to-all переводит тензоры из «шардированы по последовательности» в «шардированы по головам»
   (часть 4). Сам all-to-all вы соберёте из P2P-операций (часть 3).

Всё работает на CPU (бэкенд gloo) с 4 и 8 процессами, GPU не нужен. Корректность проверяется эквивалентностью:
обучение с CP должно повторять обучение в одном процессе, с тем же loss и той же нормой градиента на каждом шаге.

Почитать:

- Ring Attention: https://arxiv.org/abs/2310.01889; online softmax: https://arxiv.org/abs/1805.02867
- DeepSpeed-Ulysses: https://arxiv.org/abs/2309.14509

## Как устроен mtf

Начните с `mtf/train.py`: цикл обучения читается сверху вниз. Для задания важно следующее.

- **Mesh** (`mtf/dist.py`) имеет оси `(dp_replicate, dp_shard, cp)`; размер `cp` задаётся `--parallel.cp`.
  Из них собраны плоские оси `dp = dp_replicate × dp_shard` и `dp_shard_cp = dp_shard × cp`.
- **Данные** (`mtf/data.py`): все ранги одной CP-группы получают один и тот же батч `{"tokens", "labels",
  "positions"}` формы `[micro_batch, seq_len]`. `positions` — абсолютные позиции токенов, из них модель считает
  RoPE. В цикле обучения батч проходит через `shard_batch` (`mtf/parallel/__init__.py`), который оставляет
  рангу его часть последовательности.
- **Attention** (`mtf/model/transformer.py`) вызывает `self.attn_fn(q, k, v, positions)`. `apply_cp` в
  `mtf/parallel/cp.py` подменяет её у каждого блока на выбранную реализацию. Все реализации получают
  `q, k, v` формы `[B, H, S_local, D]` и `positions` формы `[B, S_local]` (абсолютные позиции локальных
  токенов) и возвращают `[B, H, S_local, D]`: строки полного causal attention, которые относятся к
  токенам этого ранга. Ключ виден запросу, если `q_pos >= k_pos`. Маску по позициям строит `causal_mask`.
  При grouped-query attention головы K/V заранее повторены до числа голов Q, так что их всегда поровну.
- **Loss** каждый ранг считает по своим токенам, а шаг оптимизатора общий: FSDP усредняет градиенты по своей
  mesh.

Писать код нужно в трёх файлах: `mtf/parallel/cp.py`, `mtf/parallel/comm.py` и одна строка в
`mtf/parallel/__init__.py`. Места помечены `NotImplementedError` и `TODO`. Остальное менять не нужно.

## Часть 1. Данные для CP и all-gather attention (3 балла)

**1.1. Разбиение последовательности.** Последовательность режется на N равных кусков подряд, ранг `r` берёт
кусок `r`. Например, при N = 2 и `seq_len = 8` ранг 0 берёт токены 0–3, ранг 1 — токены 4–7. Реализуйте
`cp_shard`. Оно применяется к `tokens`, `labels` и `positions` одинаково, поэтому метки и позиции остаются при
своих токенах.

**1.2. Градиенты.** Ранги одной CP-группы считают градиенты одних и тех же весов по разным токенам одних и тех же
последовательностей. Выберите в `parallelize` (`mtf/parallel/__init__.py`) mesh для FSDP так, чтобы шаг
оптимизатора совпадал с обучением в одном процессе. Подумайте, почему достаточно именно *усреднить*.

**1.3. All-gather attention.** В `allgather_attention` соберите K, V и их позиции со всех рангов группы и
посчитайте attention локальных запросов по всем ключам. Сбор K/V должен быть дифференцируемым: в backward
каждый ранг получает градиенты своих K/V. Используйте `torch.distributed._functional_collectives`
(у `torch.distributed.nn.functional` на gloo неверные градиенты).

**Критерии:**

| Что | Баллы |
|---|---|
| `cp_shard` (`test_cp_shard`) | 0.5 |
| `allgather_attention`: forward и backward совпадают с torch при N = 4, 8 | 1 |
| обучение с `cp_attn=allgather` повторяет один процесс: cp=4, cp=8, FSDP2×CP2, GQA | 1.5 |

## Часть 2. Ring attention (2 балла)

Ранги стоят в кольце. На шаге `i = 0..N−1` ранг `r` считает attention своих запросов по блоку K/V, пришедшему
от ранга `r − i`, и передаёт блок дальше, рангу `r + 1`. Целиком K/V не хранит никто. Результаты по блокам
сливаются **online softmax**: для каждого запроса храним выход `o` и `lse = log Σ exp(scores)` по уже
обработанным ключам. Новый блок с `(o_b, lse_b)` добавляется так:

```
lse_new = logaddexp(lse, lse_b)
o_new   = o · exp(lse − lse_new) + o_b · exp(lse_b − lse_new)
```

Пересылать блоки можно только **P2P-операциями**: `dist.isend` / `dist.irecv` или `dist.batch_isend_irecv`.
Тесты подменяют all-gather, all-to-all и прочие коллективы на функции, которые падают. Следите, чтобы send и
recv не ждали друг друга по кругу (deadlock). Ранги задаются глобальными номерами: для подгруппы есть
`dist.get_global_rank(group, r)`.

Backward должен работать. Есть два пути:
- сделать пересылку дифференцируемой: `torch.autograd.Function`, у которой backward отправляет градиент в
  обратную сторону по кольцу (сопряжённый к сдвигу — сдвиг назад). Остальное сделает autograd;
- написать backward целиком руками, как в FlashAttention: он снова проходит по кольцу и пересчитывает
  attention по блокам с итоговыми `o` и `lse`.

Attention causal, поэтому полезная работа распределена неравномерно: запросам ранга 0 нужен только его
собственный блок, а запросам ранга N − 1 — все N блоков. Блок от ранга с большим номером целиком в будущем и
замаскирован полностью. Считайте все блоки с маской, пропускать такие не нужно. С дифференцируемой пересылкой
это и нельзя: граф autograd на рангах станет разным, и P2P-операции в backward не сойдутся.

Подумайте, что будет со строкой, в которой замаскированы *все* ключи блока. Тесты проверяют forward и backward
на точное совпадение, NaN не пройдёт.

**Критерии:**

| Что | Баллы |
|---|---|
| `ring_attention`: forward и backward совпадают с torch при N = 4, 8, только P2P | 1 |
| обучение с `cp_attn=ring` повторяет один процесс: cp=4, cp=8, FSDP2×CP2, GQA | 1 |

## Часть 3. All-to-all из P2P (3 балла)

All-to-all — коллектив Ulysses и expert parallel: ранг `r` режет свой тензор по dim 0 на куски по
`input_split_sizes` строк и отправляет кусок `j` рангу `j`. На выходе — куски, полученные от рангов
`0, 1, …, N−1`, склеенные по dim 0 (по `output_split_sizes` строк). Семантика та же, что у
`torch.distributed.all_to_all_single`. В NCCL all-to-all именно так и устроен: это группа send/recv.
В torch 2.15 gloo уже умеет all-to-all, но здесь его использовать нельзя (тесты это проверяют). Зато тесты берут
его как эталон.

В `mtf/parallel/comm.py` реализуйте:
- `all_to_all_single(input, output_split_sizes, input_split_sizes, group)` на P2P-операциях. Сплиты бывают
  неравными и нулевыми, `None` значит поровну. Группа может быть подгруппой: номер ранга в группе ≠ глобальный.
- `_AllToAll`: `autograd.Function` для дифференцируемого `all_to_all`. Каким должен быть градиент, если
  all-to-all — просто перестановка строк между рангами?

**Критерии:**

| Что | Баллы |
|---|---|
| равные сплиты (в том числе `None`), N = 4, 8 | 1 |
| неравные и нулевые сплиты, подгруппы, N = 4, 8 | 1 |
| autograd: градиент совпадает с эталоном, N = 4, 8 | 1 |

## Часть 4. Ulysses (2 балла)

У каждого ранга `q, k, v` формы `[B, H, S/N, D]`: все головы, часть токенов. Первый all-to-all переводит их в
`[B, H/N, S, D]`: часть голов, все токены. Группу голов `j` получает ранг `j`, а от каждого ранга приходит
его кусок последовательности. Дальше обычное attention на своих головах, и второй all-to-all возвращает выход в
`[B, H, S/N, D]`. Используйте свой `all_to_all` из части 3. Тесты подменяют all-to-all из torch, а остальные
коллективы трогать можно. Нужно, чтобы N делило H.

Куски последовательности приходят в порядке рангов, то есть в порядке позиций: после all-to-all у ранга вся
последовательность целиком, и маска — обычная causal.

**Критерии:**

| Что | Баллы |
|---|---|
| `ulysses_attention`: forward и backward совпадают с torch при N = 4, 8, свой all-to-all | 1 |
| обучение с `cp_attn=ulysses` повторяет один процесс: cp=4, cp=8, FSDP2×CP2, GQA | 1 |

**Сравнение с эталонным обучением.** `configs/tinystories_cp.toml` — модель на ≈16M параметров (8 голов,
4 слоя, seq_len 1024) с нуля на TinyStories (токены уже лежат в `data/tinystories.bin`). Эталон — 100 шагов
в одном процессе: `reference/tinystories_1proc.jsonl` (loss 10.8 → 5.2). Запустите то же с CP и сравните:

```bash
OMP_NUM_THREADS=2 uv run torchrun --master_addr=127.0.0.1 --master_port=29511 --nproc_per_node=4 -m mtf.train \
  --config configs/tinystories_cp.toml --parallel.cp=4 --parallel.cp_attn=ring --train.run_dir=runs/ts_cp4_ring
uv run python tools/compare.py runs/ts_cp4_ring reference/tinystories_1proc.jsonl
```

На Apple M4 шаг занимает 1.3–2.4 с в одном процессе и 2–4 с с CP, все 100 шагов — 3–7 минут.

Чего ожидать. Эталон посчитан на другом процессоре, а fp32-обучение усиливает разницу в порядке суммирования:
сначала кривые совпадают почти точно, потом расходятся. В первые 40 шагов правильная реализация даёт расхождение
loss до 1e-6 и нормы градиента до 1e-4. К 100-му шагу loss расходится до ≈1e-4, норма на отдельных шагах — на
единицы процентов, и это нормально. Ошибка в реализации (например, неусреднённые градиенты) видна с первого
шага. На Apple M4 у верного решения в шагах 1–40 расхождение loss ≤3.4e-7 и нормы ≤6e-5. Память на ранг
падает с ростом N: 4.5 GB в одном процессе, 1.9 GB при cp=4, 1.0 GB при cp=8.
